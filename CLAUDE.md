# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`scope` (crate `scope-monitor`) is a cross-platform serial-monitor TUI built with `ratatui` + `crossterm`. It connects to a serial port (or an RTT target), shows received/sent data with timestamps and color, and is extensible via Lua plugins. Edition 2024, MSRV 1.92.0.

## Commands

```bash
cargo build                         # debug build -> target/debug/scope
cargo build --release               # what CI builds on Linux/Windows/macOS

cargo run --bin scope -- list       # list available serial ports
cargo run --bin scope -- serial <PORT> <BAUD>   # e.g. serial /dev/ttyUSB0 115200
cargo run --bin scope -- rtt <TARGET> <CHANNEL>  # RTT via probe-rs

cargo test --bin scope              # run unit tests
cargo test --bin scope <substr>     # run a single test, e.g. cargo test --bin scope test_rhs
cargo test --test tui_e2e           # run the end-to-end TUI tests (Unix only)
cargo test --test completions       # shell-completion tests (a missing shell skips, never fails)

cargo run --bin scope -- completions zsh   # emit a shell completion script
```

- This is a **binary-only crate** (no lib target). Use `cargo test --bin scope` — `cargo test --lib` fails with "no library targets". Unit tests live in `#[cfg(test)] mod tests` blocks inside the source files they cover. The exception is `graphics/screen.rs`: its tests are big enough (~570 lines) that keeping them inline buried the screen itself, so they sit in `graphics/screen/tests.rs`, declared at the bottom of `screen.rs` with a bare `#[cfg(test)] mod tests;`. Being a child module of `screen`, that file still reaches its private fields and associated functions, which is what most of those tests assert on — and the module stays flat (no nested `mod` groups), with its shared helpers at the top.
- **End-to-end TUI tests** are in `tests/tui_e2e.rs` (Unix only): they spawn the real binary in a PTY (`portable-pty`), connect it to a virtual serial port (`openpty`), inject keystrokes, and assert on the screen reconstructed by a `vt100` parser. The serial-RX test is `#[ignore]`d because byte transport over a PTY-backed serial port is platform dependent (`serialport` can't set baud via ioctl on a macOS PTY); run it with `cargo test --test tui_e2e -- --ignored`. On Linux, though, the PTY port *does* connect, and logs `Connected at "…"` asynchronously — usually just after the first render, i.e. in the middle of whatever a test types right after `wait_until_ready`. A test that counts lines in the scrollback (the #218 rotation tests fill a `capacity = 100` history) must start with `wait_until_settled`, which waits for that log on Linux; otherwise the log evicts one of its lines and shifts the history by one, which flaked only on the Ubuntu runner.
- `src/main.rs` has `#![deny(warnings)]`, so any compiler warning fails the build. Keep the tree warning-clean.
- Global CLI options (before the subcommand): `-c/--capacity` (scrollback lines, default 20000), `-t/--tag-file` (default `tags.yml`), `-l/--latency` (**microseconds** — every polling loop but `rtt_if::wait` treats it as µs, see below — clamped 0..=100000, default 100), `-n/--name` (session record base name, default a timestamp), `--headless` (see below). The session can also be renamed at runtime with `!rename <name>` in the command bar.
- **Shell completions** (issues #231, #236, `src/completion.rs`): `scope completions <SHELL>` prints `clap_complete`'s **dynamic** registration script (`bash`/`zsh`/`fish`/`powershell`/`elvish`), which makes the shell run `SCOPE_COMPLETE=<shell> scope -- <words>` on every Tab; `main` answers that with `CompleteEnv` as its **very first statement** (before `Cli::parse()`, which would reject the half-typed line, and before any setup — it runs on every Tab). Values therefore come from the live system: `serial` port = `serialport::available_ports()` (all kinds, deliberately not the USB-only `list::usb_ports`) with a `PathCompleter` fallback when none matches a **typed** prefix (socat/`openpty` PTYs aren't enumerated) — never for an empty word (`falls_back_to_paths`), or `scope serial <TAB>` on a machine with no ports (every CI runner) would offer `.` and the working directory; baud/`--speed` = the picker's `COMMON_BAUDS`/`COMMON_SPEEDS`; `rtt` target = probe-rs' built-in `Registry`, case-insensitive prefix. `--tag-file`/`--elf` carry `ValueHint::FilePath`: the dynamic bash hook has no `-o default` and fish's is `--exclusive`, so file names only complete because the **engine** offers them — a new path-valued arg needs a `ValueHint` too. Non-obvious constraints, all pinned by `tests/completions.rs`: (1) `Cli` carries an explicit `#[command(name = "scope")]`, because `clap_derive` otherwise names the command from `CARGO_PKG_NAME` (`scope-monitor`); (2) the `Completions` arm returns right after `Cli::parse()`, before `Config::load()` and the `See you later ^^` epilogue (the script is evaluated on every shell start-up); (3) the trigger var is `SCOPE_COMPLETE`, not clap's default `COMPLETE`, which is generic enough to be set already and would hijack every run; (4) the script calls back the bare name `scope`, not the build-time path — so to try a dev build, that build must be the first `scope` on `PATH` (e.g. `cargo install --path . --locked`) and the script regenerated from it: an older `scope` (0.6.x in `~/.cargo/bin`) ignores `SCOPE_COMPLETE`, and since the zsh hook discards stderr, Tab then silently offers nothing — while a leftover 0.6.x static `_scope` still completes subcommands but offers file names for ports; (5) the zsh registration gets a `$funcstack[1] == _scope` tail (`ZSH_AUTOLOAD_TAIL`) — clap's only `compdef`s, so on the `$fpath`/`_scope` install the first Tab after `compinit` autoloads the file and offers nothing. The install shape is identical to #231's static scripts (same files, same commands), so upgrading is re-running the same line. `unstable-dynamic` (+ `clap/unstable-ext`) is semver-exempt, hence `clap_complete = "=4.6.8"` and `clap = "~4.5.20"`: bump them deliberately and rerun the completion tests. The `Commands::Completions { .. } => unreachable!()` arm inside the closure only keeps the match exhaustive. Install instructions live in README.md → *Installation → Shell completions* and in `scope completions --help`.
- **Icon mode** (`src/selector.rs`, issues #229/#230): when `serial`/`rtt` is launched **without** its positional args (`scope serial`, `scope --headless rtt`, …), `main` runs an interactive ratatui picker *before* spawning any task, to choose port+baud (serial: a list from `list::usb_ports`) or target+channel (rtt: text fields, since a chip name isn't enumerable). `resolve_serial`/`resolve_rtt` in `main.rs` gate it: only when the missing arg *and* an interactive terminal (`stdin/stdout.is_terminal()`) are present — piped/scripted runs fall through to the old "start disconnected" behaviour, as does the picker's `Skip` (`s`). `Quit` (`q`/`Esc`) exits before the app starts. The picker owns its own crossterm session (raw mode + alternate screen) and restores the terminal via `Tui`'s `Drop`. Pure state logic (`move_selection`, `parse_baud`, `parse_channel`, `initial_baud_index`, plus `parse_speed`/`parse_address`/`initial_speed_index`/`stage_after_*` for RTT) is unit-tested; the render/loop is exercised via the `test-tui` skill. The RTT picker also asks for the probe speed and the control-block location (issue #248), each step skipped when the CLI already answered it (`stage_after_channel`/`stage_after_speed`); `parse_address` is shared with the `--addr` flag's `value_parser`, so a typo is rejected identically at the prompt and on the command line.
- **Headless mode** (`--headless`): no TUI — a raw terminal↔wire bridge. A `graphics/headless.rs` task takes the graphics slot (same `GraphicsCommand` channel + tx/rx/logger consumers) and just writes RX bytes to stdout (logs colored via ANSI, no timestamps/scrollback/persistence). The Inputs task carries a `raw: bool` overlay on `InputsShared` (not a new `InputMode`): raw keys are encoded to VT bytes (`inputs/key_encode.rs`) and sent straight to `tx`; `Ctrl+K` drops into the existing `Normal` command bar (blinking `> ` prompt rendered by the headless task), Enter runs the command and returns to raw, Esc quits. The interface tasks forward RX immediately (per-byte / per-chunk) instead of `\n`-framing when `headless` is set.
- **Periodic full repaint** (issues #166/#233): a 3s `Timer` in the graphics draw loop forces a whole-screen repaint (`graphics/graphics_task.rs`, `force_full_repaint`) so a screen cleared from outside the app (e.g. Cmd+K in Zed's terminal) heals itself. It must **not** call `terminal.clear()`: crossterm's `execute!` flushes `ESC[2J` on a write of its own, so the terminal shows a blank frame ~2ms before the repaint arrives — that was the 1Hz blink of #233. It must **not** use `terminal.swap_buffers()` alone either: a reset diff base equals a blank cell, so ratatui skips every cell that is blank in the new frame and strands stale glyphs forever. Instead the back buffer is filled with a sentinel cell and promoted to the diff base with `swap_buffers`, so the next `draw` rewrites every cell (blanks included) in its normal flush — no erase byte is ever emitted. Rewriting the blanks makes a forced frame ~3x bigger, which is what the 3s period pays for: measured idle output is ~2.4KB/s at 160x40, just under the ~2.7KB/s the old 1s clear+repaint cost. A genuine resize still clears, inside ratatui's `Terminal::resize`. Two e2e tests pin both halves (`periodic_repaint_never_erases_the_display`, `periodic_repaint_overwrites_external_garbage`); `screen_recovers_after_external_clear` alone passes even for the two broken variants.
- Optional config file (`infra/config.rs`): `<config_dir>/scope/config.toml` (e.g. `~/.config/scope/config.toml`, alongside the crash backups). Supports `capacity`, `tag_file`, `hex_format`, and the optional `[shortcuts]` and `[history]` tables (see below); the theme has its own `theme.toml` next to it. Resolution precedence is **CLI flag > config.toml > built-in default** (`Config::load` is folded into `main`'s single fatal-error flow). A missing file/field falls through to defaults; a malformed file or unknown key is a fatal error (`deny_unknown_fields`). Path values (`tag_file`) are used verbatim — there is no shell involved, so `~` and `$VAR` are **not** expanded; use an absolute path.
- **Hex format** (`graphics/screen.rs`, issue #239): the top-level `hex_format` config key restyles bytes with no text form, by **name** — `escaped` (default, `\xaa`), `prefixed_upper` (`0xAA`), `prefixed_lower` (`0xaa`), `bare` (`AA`); config.toml > default, no CLI flag. Names rather than samples like `"0xAA"`, so nobody reads the value as a template they can edit. `HexFormat` derives `Deserialize` (`rename_all = "snake_case"`) and `Config.hex_format` is an `Option<HexFormat>`, so an unknown name is rejected by the TOML parser with the file, line/column and the valid names — the same error as an unknown key, which a hand-rolled `from_config` over a `String` could not give. The format lives in `ScreenDecoder`, now a struct (`charset` + `hex_format`, built by `Screen::new`) rather than an enum. **`ScreenDecoder::decode` still always emits `\xNN`**: `ANSI` finds CSI sequences by the literal `\x1b[`, so the format can only be applied *after* ANSI stripping. `ScreenDecoder::plain_text` (decode → `ANSI::remove_encoding` → `HexFormat::apply`) is therefore the one "what the screen shows" string, and search (`collect_search_hits`/`search_line`), `MessageFilter::allows` and the clipboard (`get_selection_content`) all use it. Rendering reaches the same text a different way (`ANSI::decode` spans, then `highlight_special_characters` rewrites each `\xNN` Special span), so both sides find escapes through one shared `find_escape`. `RAW_ESCAPE_LEN` (4) is the length of that *input* `\xNN` form, not of the output — every format, `bare` included, is matched as `\xNN` and only then rewritten. Selection columns come from the screen and `AA` is narrower than `\xaa`, so any drift between the two misaligns copy and search; `rendered_line_matches_plain_text_in_every_format` pins it. `Serialize` (session files, `.bkp`) deliberately keeps `\xNN`.
- **Theme** (`graphics/theme.rs`, issue #68): a **separate** optional `<config_dir>/scope/theme.toml` (not a table of `config.toml`, so a theme can be swapped/shared on its own — `config.toml` now rejects a `[theme]` key as unknown). Top-level keys are colors **by role** (`connected`, `search`, `accent`, `hint`, `log_*`…, not by widget), the `[icons]` table holds `highlight`, `recording`, `scroll_up`/`scroll_down`, `cursor`; theme.toml > default, no CLI flag, and `Theme::default()` reproduces the pre-theming look exactly. `Theme::load` reuses `config.rs`'s `config_file_path`/`load_toml` (missing file → default, malformed → fatal, error naming the file). `Theme` derives `Deserialize` with `#[serde(default, deny_unknown_fields)]`, so an omitted key keeps its default while an unknown role is a located TOML error; colors go through a custom `deserialize_with` over ratatui's `Color::from_str` (names, `#rrggbb`, `"0".."255"`) because ratatui's own serde impl only says "Failed to parse Colors" — and it needs no extra feature. Icon widths (`scroll_up`/`scroll_down`/`cursor` must be 1 cell) are checked afterwards by `Theme::validate`, inside `Theme::load`. The theme lives in a process-wide `OnceLock` (`theme::install` in `main`, **before** the picker, which renders with it; `theme::theme()` everywhere else, falling back to the default so unit tests need nothing): it is immutable and read from ~20 render fns across `graphics_task`, `screen`, `headless` and `selector`, which a parameter would have to thread through. **Transparency** is the `background` role: a TUI can't set window opacity, only whether it paints — `reset` (default) paints nothing so the terminal's background shows through; any other color is applied by `theme::paint_background` as the **last** step of each `draw` (graphics loop and picker), filling only cells still on `Color::Reset`, so explicit widget backgrounds win. Text on a themed background uses `Palette::fg`, which now picks black/white by luma for `Rgb`/`Indexed` (it used to return `Reset`, unreadable on a custom bg). Headless log SGRs are derived from the theme via `Palette::sgr_fg`/`sgr_bg`; a test pins that the default theme still emits the historical `\x1b[97;41m`… sequences.
- **History autosave** (issue #247): the optional `[history]` config table has two booleans, both default `true`, no CLI flag (config.toml > default). `save_commands = false` builds the Inputs task's history as `AnyHistory::Base` (in-memory only — the `.scope_history` file in `<data_dir>/scope` is neither read nor written); `save_backup = false` gives Graphics a `Backup::disabled()` (no worker thread, `append`/`rename` are no-ops, no `.bkp` or backup dir created). They are resolved once into `config::Autosave` in `main` and threaded through `app_serial`/`app_rtt` — `InputsConnections::new` gets `autosave.commands`, `GraphicsConfig` gets `save_backup`. Explicit saves (`Ctrl+S`, `!record`) are unaffected. The reporter's alternative (`log_write`/`log_read`, split by direction) was rejected: it would leave the `.bkp` partial and no longer byte-identical to the saved `.txt`.
- **Custom shortcuts** (`inputs/keymap.rs`, issue #211): the optional `[shortcuts]` config table (`action = "Key+Combo"`) remaps the 15 action/navigation keys. `Action`/`KeyBinding`/`Keymap` own all key knowledge; `config.rs` stays a `BTreeMap<String,String>` and never enumerates the actions. Shortcuts have no CLI flag, so precedence is config.toml > default; `Keymap::from_config(config.shortcuts)` is built in `main` and threaded (by value, no lock) through `app_serial`/`app_rtt` into `InputsConnections`. Config modifier names are **logical** and lowered to the real per-platform crossterm event in `keymap::resolve` — this replaces the old `CTRL_MODIFIER`/`ACTION_MODIFIER` consts in `handle_key_input` (only `ACTION_MODIFIER`, for the fixed `Alt+Enter` arm, remains). `handle_key_input` resolves a remappable action via `private.keymap.action_for()` **before** the intrinsic key match (`try_run_action`); a `Tab`-bound `next_bookmark` falls through to the `@tag` autocomplete arm while the pop-up is up. Text-editing/intrinsic keys (typing, Enter, Esc, arrows, Home/End, Backspace/Delete, headless `Ctrl+K`/`Ctrl+Q`) stay hardcoded and are rejected as override targets (`reserved_reason`). Unknown actions, bad key strings, reserved keys and duplicate bindings are fatal config errors. An unbound `Ctrl`/`Alt`+letter is now swallowed rather than typed literally.
- **RTT control block discovery** (`interfaces/rtt_if.rs`, issue #248): attaching used to scan a hard-coded `0x2000_0000..0x2000_8000` — the conventional Cortex-M SRAM base — so on any part whose RAM lives elsewhere the cheap probe could never hit and *every* attach paid for a full-RAM sweep (3.2s on an i.MX RT1021, whose application RAM is OCRAM at `0x2020_0000`). `scan_region` now resolves the window from the target, in order: `--addr` → `--elf` (the `_SEGGER_RTT` symbol, read by `interfaces/rtt_elf.rs` via the `object` crate) → the target description's own `rtt_scan_regions` when it names them → the first 32KiB (`SCAN_WINDOW`) of **every** RAM region in `core.memory_regions()`. Only the last one falls back to `Rtt::attach` (whole RAM); an `Exact` address from the user deliberately does **not**, since a sweep would spend exactly the time they asked to save. A missing/stale `--elf` is warned about and degrades to scanning — it costs speed, not the connection. `scan_region_in` is the pure half (no live `Core`) and is where the precedence is unit-tested. `--speed` replaces the hard-coded 4000kHz (`DEFAULT_PROBE_SPEED_KHZ`). All four settings travel in `RttSetup` (also the picker's return type and `resolve_rtt`'s argument, so `main` stops juggling a tuple), and `RttShared` holds them for `connect`. The recurring-failure dedupe strings moved into one `LastLogged` struct so adding the RTT-attach error did not add a 9th parameter to `connect`/`disconnect`/`setup`. Deliberately **no** `[rtt]` section in config.toml: the block address and ELF path change per build, so the picker asks for them instead.
- `Ble` is declared as a subcommand but is not implemented (returns an error).
- **Release & installers** (issue #229): distribution is driven by [cargo-dist](https://opensource.axo.dev/cargo-dist/) — config in `dist-workspace.toml` (`[dist]`), the `[profile.dist]` profile and `[package.metadata.wix]` GUIDs in `Cargo.toml`. `.github/workflows/release.yml` is **dist-generated** (do not hand-edit; regenerate with `dist init && dist generate`) and fires on a `vX.Y.Z` tag, building tarballs/zip + shell/powershell installers + a Windows `.msi`. Publishing to crates.io is *not* done by dist — `.github/workflows/publish-crates.yml` handles that on the same tag (OIDC). Maintainer release flow: open a PR bumping the version, label it `release`, merge it — `release-tag.yml` creates the tag from that merge (see the next bullet), so there is no manual tagging step. PRs only run `dist plan`; to test the `.msi` before a tag, temporarily set `pr-run-mode = "upload"`, `dist generate` and push — the PR then builds the full artifact set and attaches it to the Actions run without publishing (`gh run download <run-id>`) — then revert it. `wix/main.wxs` is hand-edited (dist `allow-dirty = ["msi"]`) to add the four per-command Start-Menu shortcuts + their icons; `libudev-dev` is installed on the Linux runner via `[dist.dependencies.apt]`.

Repo-settings pieces (rulesets, environment reviewers) live in GitHub, not the tree.
- **Tagging from the release PR** (`.github/workflows/release-tag.yml`): the tag is not pushed by hand — merging a version bump into `main` cuts it, so the release is a single maintainer-gated flow. Non-obvious constraints: (1) it triggers on **`push`**, never `pull_request` — a `push` run always takes the workflow definition from `main`, whereas a `pull_request` run would use the *PR branch's* copy, letting a PR rewrite the file that holds the tagging token; (2) the tag is pushed with a maintainer PAT (`RELEASE_TAG_TOKEN`, from the `release-tag` environment) because a `GITHUB_TOKEN` push **does not trigger other workflows** (`release.yml`/`publish-crates.yml` would never fire) and tag creation is admin-only per the ruleset — the owner's PAT also keeps `github.actor` on the tag push equal to the owner, so `publish-crates.yml`'s owner guard still holds. Guards: owner-only pusher, the merged PR must carry the `release` label (the same one `version-guard` needs for the bump, making it the single release opt-in), the version must actually have changed (`paths: Cargo.toml` also fires for dependency edits), and an existing tag is never moved. Its `GITHUB_TOKEN` stays `contents: read`. Four invariants are pinned in `tests/release_security.rs`. PAT setup lives in CONTRIBUTING.md → *Release security → One-time setup for automatic tagging*.
- **Claude's pushes and PRs go through `matheuswhite-bot`**, so the owner can approve them: GitHub won't let an author approve their own PR, and the `main` ruleset requires 1 approval, `require_last_push_approval` (the most recent reviewable push must be approved by someone other than whoever pushed it), signed commits and resolved threads. Every push and PR Claude makes in this repo is done as the bot, never the owner's account: `GH_TOKEN` comes from `.claude/settings.local.json` (git-ignored), and `gh api user --jq .login` must print `matheuswhite-bot` before anything is pushed (stop and tell the user otherwise). `origin` is SSH, i.e. the owner, so push to the HTTPS URL with `GH_TOKEN` exported: `git push https://github.com/matheuswhite/scope-rs.git HEAD:refs/heads/<branch>`. The owner's global git config already routes `https://github.com` credentials through `gh auth git-credential` (`gh auth setup-git`), which answers with `GH_TOKEN`, so no `-c credential.helper=…` is needed; a worktree-isolated session refuses that flag anyway. Open PRs with `gh pr create --assignee @me --reviewer matheuswhite`, and read reviewers through REST (`pulls/<n>` → `.requested_reviewers`), since the GraphQL `reviewRequests` field needs `read:org`, which the token lacks. Non-obvious, all hit on #271: (1) commits stay authored and SSH-signed by the owner, so the commit avatar shows the owner even when the bot pushed. Who pushed is in `gh api "repos/matheuswhite/scope-rs/activity?ref=refs/heads/<branch>"`. (2) If the push is run without `GH_TOKEN` exported, `gh auth git-credential` silently falls back to the owner's own gh login and the push becomes the owner's, so check the identity right before every push, and gate any push the user runs by hand: `[ "$(gh api user --jq .login)" = matheuswhite-bot ] && git push …`. (3) Only a push that **changes the PR's diff** counts as the reviewable push: re-pushing the same content as the bot (amend, a same-tree force-push) carries the old approvals over but leaves the owner's push as the one that needs approval. To take it over with commits already on GitHub, move the branch back one commit and forward again through the API (`gh api -X PATCH repos/matheuswhite/scope-rs/git/refs/heads/<branch> -f sha=<parent> -F force=true`, then `-f sha=<head>`); the approval is dismissed and the owner approves again.

## Architecture

The app is a **multi-threaded actor system**. `main.rs` (`app_serial` / `app_rtt`) wires everything up, spawns four long-lived tasks on their own OS threads, and `join`s them. The two app functions are near-duplicates differing only in which interface (serial vs RTT) they spawn.

### Tasks and shared state (`infra/task.rs`)

Every subsystem is a `Task<S, M>`: it owns shared state `S` behind an `Arc<RwLock<S>>` and receives `M` commands over an `std::sync::mpsc` channel. Other tasks get a **read-only** `Shared<S>` handle (`task.shared_ref()`) to observe state, and a `Sender<M>` to drive it. The four tasks:

- **Interface** (`interfaces/`) — owns the serial port or RTT connection. Enum-dispatched: `InterfaceTask` / `InterfaceCommand` / `InterfaceShared` / `InterfaceType` select between `serial_if.rs` and `rtt_if.rs`.
- **Inputs** (`inputs/inputs_task.rs`) — the command bar. Parses keystrokes, manages input history (`inputs/history.rs`), and has two `InputMode`s: `Normal` and `Search` (plus a `raw` passthrough flag used only in headless mode).
- **Graphics** (`graphics/graphics_task.rs`) — renders the TUI, owns the scrollback buffer, handles selection/scrolling, persists the session to a timestamped `.txt` file, and is the sink for log messages. **Scrolling up freezes the view** (`Screen::auto_scroll`), and staying frozen while the buffer rotates is what issue #218 was about: `Screen::position.line` is a buffer *index*, but at capacity every new line evicts the oldest and re-indexes the rest, so a fixed offset let the content slide upwards under a "frozen" viewport (hence the bug only appearing after the first `--capacity` lines). `Buffer` therefore counts lifetime front-evictions (`Buffer::evicted`, reset by `clear` in lockstep with `Screen::clear`) and `Screen::update_after_new_lines` slides the offset — and any active selection, via `Selection::shift_up` — by the growth of that count. Offset 0 is the floor: there the lines on screen are the ones being dropped, which is what `--capacity` buys. `Buffer` holds a `VecDeque` so the per-line eviction is a `pop_front`, not a whole-history memmove. **Search is positional too**, and was the other half of #218: its hit list is re-scanned from the buffer on every batch of new lines, and the old code re-scanned by re-arming the query (`update_search_state`), which reset `current` to 0 and re-centred the viewport on the first hit — so under a live stream the frozen view was yanked back on every batch and `Enter`/`Up`/`Down` could not advance at all. That path is now split: `update_search_state` (user changed the query, or the filter changed which lines exist) still re-arms and jumps, while `refresh_search_hits` (new lines landed) re-scans with neither the viewport nor `current` moving. A hit is therefore a `SearchHit { position, line_id }` — `position` is what a re-scan invalidates, the stable `line_id` is what identifies the hit the user is on across one (`ScreenMode::take_hits_for_rescan` / `restore_current`, falling back to the first hit at or after that id, ids being monotonic). The highlight of the chosen match keys off the id for the same reason. In headless mode it is replaced by `graphics/headless.rs` (same task slot, plain stdout, no TUI). Line-pinned features (bookmarks: right-click to toggle, `Tab`/`Shift+Tab` to jump, yellow timestamp) live in `graphics/screen.rs` and key off the stable per-line `BufferLine::id` so they survive scrollback rotation and filter changes. Surviving a *filter* change needs one more thing: `rebuild_displayed_buffer` re-anchors the screen with `Screen::rebase_on_rebuilt_buffer` (viewport back to the bottom, positional selection dropped, eviction count restarted alongside the buffer's), **not** `Screen::clear` — clear additionally drops the bookmarks and is reserved for `Ctrl+L`, which throws away the history they point into.
- **PluginEngine** (`plugin/engine.rs`) — runs a Tokio runtime hosting Lua plugins.

### Data buses (`infra/mpmc.rs`)

Two custom fan-out MPMC channels carry `Arc<TimedBytes>` payloads. A `Producer::produce` clones the payload to **every** registered `Consumer` (with optional loopback exclusion by consumer id):

- **`tx_channel`** — bytes to transmit. Consumers: interface (writes to wire), plugin (so `on_*_send` hooks see it), graphics (so it's displayed).
- **`rx_channel`** — bytes received from the wire. Consumers: plugin (`on_*_recv` hooks), graphics (display).

Consumer/producer counts are fixed in `main.rs` (`tx_channel` has 3 consumers, `rx_channel` has 2); adding a consumer means updating those counts.

### Command-bar syntax (parsed in `inputs/inputs_task.rs`)

What the user types is transformed before being sent:

- **`$..` hex sequences** — `replace_hex_sequence` turns `$01 02`, `$0102`, `$01$02` into raw bytes. `,`, `_`, `-`, `.`, space and `$` act as separators between bytes within a sequence. **`$$` is the escape for a literal `$`** (issue #215): a lone `$` is always consumed as a hex marker, so `$$` emits one `$` byte and drops back to text mode (`$$01` -> `"$01"`, `$41$$41` -> `A$41`); a pending single nibble is flushed before the escaped `$` so bytes stay ordered. The parser peeks one char ahead (`chars.next_if_eq(&'$')`) for this, which is why the loop is a `while let` over a `Peekable` rather than a `for`.
- **`@tag` tags** — `replace_tag_sequence` + `infra/tags.rs` resolve `@name` to a value from the tag file (default `tags.yml`, a YAML `name: value` map). `@` and whitespace delimit a tag name.
- **`!plugin args`** — invokes a Lua plugin command.

Special-character rendering for the display lives in `graphics/special_char.rs` (the `to_special_char` iterator that splits text into `Plain`/`Special` runs for highlighting). Both the tag filter and this iterator share the `SpecialCharPosition` type.

### Plugins (`plugin/`)

Plugins are Lua scripts (mlua, `lua54` vendored) returning a table `M`. The engine calls lifecycle/event hooks by name: `on_load`, `on_unload`, `on_serial_connect`/`on_serial_disconnect`/`on_serial_send`/`on_serial_recv` (and `on_rtt_*` equivalents), plus any `M.<name>` the user calls via `!plugin <name>`. Plugins reach back into the app through the `bridge`/`method_call` gates. See `plugins/README.md` for the plugin developer guide.

- **Receive hooks** (issue #250): the RX bus does not carry a fixed shape — the interface tasks `\n`-frame it (with a 1s idle flush of a partial line) only in the TUI, and forward per byte (serial) / per read chunk (RTT) in headless — so the legacy `on_serial_recv`/`on_rtt_recv` hook, which gets each bus message as-is, behaved differently per mode. It is kept for compatibility but **deprecated** (a warning is logged in `load_plugin`, which every load/install/reload/autoload goes through). The mode-independent hooks are `on_*_recv_byte(byte)` (a number, once per byte) and `on_*_recv_line(line)` (bytes, `\n` included). The engine re-frames the stream itself (`plugin/rx_lines.rs`, `RxLines`) instead of trusting the bus: a partial line is **never** delivered (not even by the TUI's idle flush), is reset on `*Disconnected`, and is dropped past 64KiB. Hook names live in `engine.rs` → `RecvHooks`. The engine drains the RX bus each pass (`while let`), since headless publishes one message per byte, and spawns the byte/line hooks only for plugins that define them (`Plugin::defines`) — every spawned call is a task plus its own response channel (`plugin/bridge.rs`).

- **Installed plugins** (`plugin/installed.rs`, issues #36/#37): `!plugin install <file>` loads a plugin *and* records its name in a TOML manifest `<config_dir>/scope/plugins/installed.toml` (next to the staged `.lua` files); `!plugin uninstall <name>` removes it from the manifest and deletes the staged copy; `!plugin list` prints the set. The engine owns the manifest: `PluginEngineCommand::{InstallPlugin,UninstallPlugin,ListInstalledPlugins}` handle the commands, and `load_installed_plugins` (called once at the top of `task_async`, before the command loop) auto-loads each installed plugin from its staged copy, logging per plugin like `!plugin load`. Install persists only after a successful load, dedupes, and treats a missing/malformed manifest or a broken entry as logged-and-skipped (never fatal — it's program-managed state, not the user's `config.toml`). Uninstall errors if the plugin isn't installed and is orthogonal to `unload` — it does **not** stop a running instance (that's `!plugin unload`); the name is normalized via `get_plugin_name` so `foo`/`foo.lua` both work, and it never deletes a bundled `STDLIB` file (`plugin/stdlib.rs`: `scope.lua`/`shell.lua`/`codec/at.lua`) even if a hand-edited manifest lists a reserved name.

- **Test framework, `send_and_wait`, `M.config`** (issue #251): most of it is Lua in `plugins/scope.lua`; Rust only adds what Lua cannot do. Non-obvious points: (1) the bundled stdlib (`plugin/stdlib.rs`, now with `codec/at.lua` in a subdirectory) is **rewritten on every load when it differs** — it used to be written only when missing, which left existing users on an old `scope.lua` without the new API forever. (2) `Plugin::new` puts the plugin directory **first** in `package.path`, set through the mlua API rather than a `format!`ed Lua string (a Windows path's backslashes would be read as escapes): appended after Lua's default `./?.lua`, a stale `scope.lua` in the working directory won every `require("scope")`, and once `_init_config` existed it broke every load. It then runs `require("scope")._init_config(M)` before `on_load`, so `M.config` always exists with defaults (`at.lua`-style plugins assign `M.config.x` in `setup_suite`); `scope.lua` reads it lazily through the global `M` at each use, and Rust reads `recv_as_string` per spawned hook (`RecvData`). (3) `send_and_wait` is an engine request, not a `serial.recv` loop. Calls go through a `WaitQueue` (`plugin/line_waiter.rs`) that keeps **one** on the wire at a time, whichever plugin made it: a queued call is sent when the one before it ends, and its timeout starts then — with every waiter fed every line, one `OK` used to end all of them. Each engine pass runs commands → RX drain → timeouts → requests → TX hooks, so a call is sent only after the lines received so far were framed (a line that arrived before the send never answers it) and a reply already on the bus beats the timeout. Patterns are `regex::bytes`, anchored to the whole line (`^(?:p)$`), empty lines are dropped, and the result is `lines, matched` or `nil, "timeout"`/the error line; `scope.lua` validates the options first (whole-number timeout, `ignore_msg` a list of strings) so a bad value is a Lua error a suite can catch, not an abort in Rust. (4) Each method call has its own unbounded response channel, keyed by an id the engine allocates (`PluginEngineGate::new_method_call_gate`/`respond`/`finished`): the old 32-slot broadcast could lag and kill a call parked in a long wait. Each `Plugin` tracks the ids of its running calls (`owns`): a request from a call its instance no longer owns (unloaded, or reloaded meanwhile) is answered `PluginResponse::Unloaded`, which stops the call ("Stopped: the plugin was unloaded"), and when `on_unload` finishes, the instance's pending waits and `recv`/`rtt.read` requests are cancelled the same way — a suite parked there used to never send `Finish`, leaving `!test` refused for the rest of the session. (5) `!test` is resolved by `plugin/suite.rs` (`select`: a loaded plugin name wins over a test name; tests are ordered by `Function::info().line_defined`), and the suite runs as one coroutine (`Entry::TestSuite` → `suite.lua` → `scope.test._run_suite`). `running_suites` (plugin → method id, cleared on that call's `Finish` before the owner check) refuses a second concurrent suite. `test` is a reserved plugin name, like `scope`/`shell`, which is why the old `plugins/test.lua` sample is now `sample.lua`. (6) Asserts raise a table with a `Signal` metatable (`__tostring`, which `thread.lua`/`unpack.lua` now call), and take the failing line from `pcall(error, "", 4)` — valid only while each assert calls `fail` directly, not as a tail call. (7) The plugins directory is injected through `PluginEngineConnections` (`main` passes `engine::plugins_dir()`), so the engine tests (`Rig` in `engine.rs`) run the real engine against a temp dir and a fake device on the TX/RX buses — a suite through `send_and_wait`, an unload mid-suite, two plugins' calls taking turns; the Lua stdlib itself is tested in `plugin/stdlib.rs` with a Lua driver that answers the yielded requests.

## Logging

`infra/logger.rs` provides a channel-based logger; each task gets a clone tagged with its source name. Use the `error!`, `warning!`, `success!`, `info!` macros — messages fan in to the Graphics task for display.

## Manually testing the TUI

There is a `test-tui` skill (`.claude/skills/test-tui/`) that drives the running TUI end-to-end without hardware: a virtual serial port via `socat`, the app inside `tmux`, keystroke injection with `tmux send-keys`, and screen/colour inspection via `tmux capture-pane`. Use it to verify send/receive behavior and visual layout.
